## 1. The test for "unnecessary"

Remove something when a reader who knows the stack gains nothing from it, and nobody depends on it. Keep it when it carries information the code cannot: why a decision was made, a constraint from outside the code, a legal requirement, or a warning about a trap. When unsure, keep it and move on. The costs are asymmetric: an extra comment is cheap, lost context is not.

## 2. Comments

**Remove (Tier A)**

- Comments that restate the next line: `// increment counter`, `# loop over users`, `// import dependencies`, `// return the result`.
- Narration of the writing process: `// Added this to fix the bug`, `// Updated to use the new API`, `// Step 1: ...` where the steps are obvious from the code, `// Now we...`, `// Let's...`.
- Section banners and dividers made of ASCII art or repeated characters (`// ===== HELPERS =====`) unless the file is long and the banner truly aids navigation. Prefer splitting the file.
- Commented-out code. Version control remembers it.
- Placeholder comments: `// TODO: implement`, `// your code here`, `// add error handling` left in finished code. If the work is real, either do it or turn it into a tracked issue and remove the comment.
- Emoji in comments, log messages, and commit-style notes.
- Comments naming the generator: "Generated by ...", "AI-generated", "Created with ...".
- Stale comments that contradict the code. Fix or delete.

**Keep (Tier C)**

- Why-comments: the business rule, the workaround for a specific library or browser bug (with a link or version), the performance reason for an unusual structure, the reason a naive approach fails.
- Public API documentation: docstrings and JSDoc on exported functions, types, and modules, particularly for libraries.
- License and copyright headers.
- Type-checker and linter directives (`// @ts-expect-error`, `# noqa`, `// eslint-disable-next-line`) that are still needed. Review each: if the suppression is no longer necessary, remove the directive and fix the cause.
- Region markers or annotations that tooling reads (`// prettier-ignore`, `#region`, `/* istanbul ignore */`, `<!-- prettier-ignore -->`).
- TODOs with a ticket or owner and a real deadline. Ask the user about the rest.

Comment syntax to search by language: `//` and `/* */` (JS, TS, Go, Java, C family, Rust, Swift, Kotlin), `#` (Python, shell, Ruby, YAML, TOML), `--` (SQL, Lua), `<!-- -->` (HTML, Markdown, JSX in `{/* */}`), `"""` docstrings (Python).

Do not mass-delete with a regex. Review in context, file by file, or use a formatter-safe approach (edit by hand or with a script that only targets patterns you have verified). Keep formatting churn out of the diff: do not reflow code or change whitespace beyond the removed lines.

## 3. Dead code and debug output

- `console.log`, `print`, `println!`, `fmt.Println`, `debugger`, `dd()`, `var_dump` used for debugging. Keep deliberate, structured logging.
- Unused imports, variables, functions, components, and exports. Use the project's linter or a dead-code tool first (`eslint` with `no-unused-vars`, `knip` or `ts-prune` for TypeScript, `vulture` for Python, `deadcode` or `staticcheck` for Go).
- Unreachable branches and feature flags that are permanently on or off.
- Duplicate implementations of the same helper. Consolidate to one, update imports.
- Mock data and fake API responses wired into production paths. Move test doubles into test directories or delete.

## 4. Files and folders

**Usually remove (Tier B, list before deleting unless obviously junk)**

- Scratch and backup files: `*.bak`, `*.orig`, `*.old`, `*~`, `copy of ...`, `file (1).ext`, `test.js`/`temp.py` at the root, `untitled`.
- Leftover scaffolding: framework starter pages and assets that the app no longer uses (default logos, sample routes, example components, boilerplate CSS, `hello-world` endpoints).
- Generated artifacts committed by mistake: `dist/`, `build/`, `.next/`, `coverage/`, `__pycache__/`, `.DS_Store`, `Thumbs.db`, `*.log`, IDE folders (`.idea/`, `.vscode/` unless the team shares settings intentionally).
- Planning and note files produced during development: `PLAN.md`, `NOTES.md`, `TODO.md`, `SUMMARY.md`, `IMPLEMENTATION.md`, `PROGRESS.md`, `CHANGES.md` when they are working notes rather than real project documentation, and duplicated or contradictory variants of the README.
- Empty files and empty directories, stub modules never imported.
- Unused images, fonts, and static assets (verify by searching for references first).
- Duplicate configuration (two lint configs, two formatter configs, both `package-lock.json` and `yarn.lock`). Keep the one the project actually uses.

**Ask first (Tier C)**

- `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.cursor/`, `.windsurfrules`, `.github/copilot-instructions.md`, and similar assistant configuration. They may be intentional. Offer to remove if the user wants no assistant traces in the repo.
- CI workflows, Dockerfiles, `Makefile`, scripts used by teammates, `.editorconfig`, `.nvmrc`, `.husky/`.
- Lockfiles, migrations, seed data used by tests or onboarding, changelogs with real history.

## 5. Documentation and README

Goal: documentation that is short, true, and useful to the next person.

README should contain:

1. What the product is, in one or two plain sentences.
2. Requirements and how to install and run it, with commands verified by actually running them.
3. Configuration: required environment variable names (point to `.env.example`), and where real values are kept.
4. How to test and build.
5. Deployment notes if they are real.
6. License, if applicable.

Remove or fix:

- Marketing tone, superlatives, and feature lists that are not implemented.
- Sections for features that do not exist, roadmaps that were never real, and "coming soon" lists.
- Emoji-decorated headings and bullet walls. A few well-chosen headings beat many.
- Duplicate content copied across several docs files.
- Setup steps that do not work. Run them or delete them.
- Screenshots that no longer match the product.
- Fake or unverifiable statistics, benchmarks, testimonials, and user counts. Never invent replacements; ask the user for real data or omit the claim.
- Contributor boilerplate (code of conduct, contributing guide, issue templates) copied from templates for a project that does not use them. Keep if the project is open source and intends to accept contributions.

Inline docs (`docs/` folder): keep what is accurate and referenced, merge small fragments, delete stale files. Docs must agree with code; spot-check commands, paths, and endpoint names.

## 6. Badges, pills, and product claims in the UI

README badges:

- Keep badges that report live, meaningful status for a public project: CI status, latest release, license, coverage if actually measured.
- Remove decorative badges: "made with love", "PRs welcome" when untrue, technology logo walls, "AI-powered", vanity counters, dead links, badges that reference services the project does not use or that 404.

UI pills, chips, ribbons, and banners in the product:

- Remove claims the product cannot back up: "AI-powered", "Powered by GPT", "#1", "Trusted by 10,000+ teams", "Secure & private", "99.9% uptime", "Award-winning", fake ratings or review counts.
- Remove status pills that carry no information: "New" on features that are not new, "Beta" on stable features (or the reverse if the product really is beta), "Pro" labels with no plan behind them.
- Remove decorative sparkle icons and promo ribbons that do not map to a real feature or campaign.
- Remove "Built with ..." footers unless the user wants attribution or a license requires it.
- Keep pills that reflect real data (order status, stock level, plan tier, role) and that follow the design system. Make sure they do not rely on color alone to communicate meaning.

When removing a claim leaves a layout gap, adjust the layout through the shared component or style layer rather than leaving empty space, and follow the project's UI conventions (see `production-ui-ux-and-centralized-styling` if present).

## 7. Placeholder and filler text

Search for and resolve: "Lorem ipsum", "Your text here", "Sample", "Example Inc", "John Doe", "Jane Smith", "test@test.com", "123 Main St", "Company Name", "Insert description", "Coming soon", `example.com` links, `#` hrefs, `href="javascript:void(0)"`, dummy phone numbers, stock-image placeholders with fake alt text, Next/Vite/CRA default titles and meta descriptions, default favicon.

- If the real content is unknown, do not invent it. Flag each to the user in the report with the file and a suggested replacement source.
- Seed and demo data used for local development can stay if it lives in clearly marked seed or fixture files, not in production code paths.
- Fix page titles, meta descriptions, Open Graph tags, and the web manifest, which often retain framework defaults.

## 8. Dependencies and scaffolding

- Unused dependencies (`depcheck`, `knip`, `npm ls`, `pip-extra-reqs`, `go mod tidy`). Verify by build and test before removing, and check dynamic imports and config-referenced packages first.
- Duplicate libraries solving the same problem (two date libraries, two HTTP clients) where one is clearly unused.
- Packages with install scripts or unfamiliar names that were added by generation and are not used: remove and, if unknown, flag to the user.
- `package.json` metadata: real name, description, version, repository, license, and no leftover template values (`"name": "vite-react-typescript-starter"`). Add `"private": true` for applications not meant for npm publishing.
- Scripts that no longer work or are never used.

## 9. Keep list (leave alone unless asked)

License files and headers, real changelogs, migrations, lockfiles for the package manager in use, CI and deployment config, test files and fixtures, type declarations, accessibility annotations (`aria-*`, alt text), i18n files, comments that explain why, and anything referenced by build or runtime configuration you have not fully traced.

## 10. Tiers and process

| Tier | Examples | How |
|---|---|---|
| A | Redundant comments, commented-out code, debug logs | Apply directly, commit by category |
| B | Files, docs, badges, pills, dependencies, placeholder text | Present a short list with paths and reasons; apply after confirmation. Plainly generated junk (`.DS_Store`, `.bak`, empty stubs) can go without asking |
| C | Tooling configs, license headers, why-comments, migrations | Leave, or ask explicitly |

Process: branch, baseline, change by category, commit per category, verify, report. Do not mix secret fixes with cleanup in the same commit so each can be reviewed and reverted on its own.

## 11. Verifying that removals were safe

- Before deleting a file, search for references to its name and path across the repo, including config files, build scripts, route definitions, and dynamic imports built from strings.
- Before removing an export, search for imports of it, including barrel files (`index.ts`) and re-exports.
- Before removing a dependency, search source and config for its name and for its binaries (scripts, CI).
- After each batch: build, typecheck, lint, run tests, and if possible smoke-test the main flow.
- Review the final `git diff --stat` and spot-check a sample of removals by reading the diffs.
- Report anything that could not be verified (no tests, no way to run the app) so the user knows where to look.
